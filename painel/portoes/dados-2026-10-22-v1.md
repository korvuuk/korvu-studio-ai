## Achados que bloqueiam

### S0-1 · `anon` e `authenticated` têm privilégios nas 11 tabelas; `service_role` tem mais do que SELECT
- **Onde:** `supabase/migrations/20261022200000_leitura_do_app.sql` linhas 3–5 (só dá SELECT ao `service_role` e não
  revoga nada) e `20261022190000_inicial.sql` linha 3 (o comentário diz "Nenhuma política para anon: RLS fechado").
  No banco real (127.0.0.1:55322, contêiner `supabase_db_content-ai-painel`):
  - `has_table_privilege` em todas as 11 tabelas do `public`:
    `anon` = `TRUNCATE, REFERENCES, TRIGGER, MAINTAIN` · `authenticated` = igual ·
    `service_role` = `SELECT, TRUNCATE, REFERENCES, TRIGGER, MAINTAIN`.
  - Origem: o default ACL do schema `public` para o papel `postgres` (`pg_default_acl`:
    `anon=Dxtm, authenticated=Dxtm, service_role=rDxtm`). Nenhuma migração declara nem revoga isso. Prova: as duas
    migrações aplicadas num banco limpo dão **zero** desses 99 grants (33 por papel); só existem no banco real.
- **Regra:** `portao-dados.md` §4 — "`anon` e `authenticated` sem privilégio nenhum; `service_role` só o necessário.
  Falha = S0". Também §3 (algo no banco que não está em migração); contado uma vez só, na classe maior.
- **Cenário concreto:** o RLS não cobre `TRUNCATE` nem `TRIGGER`. Hoje a API (PostgREST/pg_graphql) não tem operação
  de TRUNCATE, então **nenhum pedido com a chave anon apaga as tabelas hoje**: digo isso para o risco ficar do tamanho
  certo. O defeito está noutro lugar. (1) Toda tabela nova herda os mesmos grants sozinha. (2) Qualquer caminho que rode SQL
  como `anon`/`authenticated` (uma função RPC ou uma view acrescentada depois) consegue `TRUNCATE metricas` sem que
  nenhuma política o impeça. (3) O README já prevê "subir para um domínio… `supabase db push`": lá a chave anon é
  pública por definição e as migrações não fecham nada. Se isso acontecer, o painel mostra o desempenho vazio até a
  próxima passagem do sincronizador. E o comentário da migração afirma o contrário do que o banco faz: é o auto-relato
  que o portão existe para pegar.
- **O que precisa mudar (engenheiro-backend):** migração nova que
  `revoke all on all tables in schema public from anon, authenticated`;
  `revoke truncate, references, trigger, maintain on all tables in schema public from service_role`;
  e o mesmo em `alter default privileges for role postgres in schema public …` (tabelas, e por defesa também
  sequências/funções para `anon`/`authenticated`). Mais um teste que falha se `has_table_privilege` der verdadeiro
  para `anon`/`authenticated` em qualquer privilégio, ou para `service_role` em algo além de SELECT.
